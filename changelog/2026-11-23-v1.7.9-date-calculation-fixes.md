Version 1.7.9 is a fixes-only release. It corrects several date calculation faults and brings in the fixes from builds 1.7.7.1 to 1.7.7.4, which were sent directly to a small number of sites in May 2026 and were never offered as an automatic update.

## After you update

The first time an administrator opens the WordPress admin, the stored dates of all published events are rebuilt. You will see a notice confirming it. There is nothing to re-save.

If a rebuild moves the dates of an event, any exclusions, overrides or reschedules you had set on the old dates will no longer line up with the new ones. This can only affect events that repeat every two or more weeks across New Year 2027, described below. Check those events after updating.

## Fixed

### The last date of a series ending on a date is no longer dropped

When a repeating event was set to end on a specific date and one of its dates fell on that day, the final date could go missing from the calendar, lists and the event's own list of dates. It happened when the event was saved earlier in the day than its start time. A weekly 6:00 PM event ending on 31 December, saved at 1:00 PM, stopped at 24 December.

The whole of the end date is now included, whatever time the event is saved. Events that end after a number of occurrences, and custom-date events, were not affected.

### Events repeating every 2 or more weeks no longer slip a week after New Year 2027

2026 has 53 calendar weeks. A weekly event repeating every 2, 3 or more weeks could move to the wrong week once it passed the end of the year. An event every 2 weeks on Thursday from 17 December 2026 showed 7 January 2027 where it should show 14 January, and stayed a week out from then on.

Weeks are now counted correctly across the year end. Events repeating every week, and daily, monthly, yearly and custom-date events, were not affected.

Events that started in 2020 or earlier have been a week out since January 2021 and will move back to their original pattern. If you have already shared January 2027 dates for an affected event, check them after updating.

### "No caching" no longer freezes an event's next date

With Cache Duration set to "No caching", an event's next date was stored the first time it was viewed and then never refreshed, so single event pages kept showing a date that had passed. The setting did the opposite of its name.

"No caching" now works as described: dates are calculated on every view. Dates stored by earlier versions are removed when you update. Sites using 15 minutes, 1 hour, 6 hours or 24 hours were not affected.

### The next date of an event that has not started is no longer before its first date

For a weekly event, or a monthly event set to a weekday of the month, whose first date was still in the future, the next date could be an earlier date on which the event does not run. The next date is now the event's first date.

This showed in the next date, time and countdown shortcodes and tags, the Next Occurrence column in the admin event list, and the start date in structured data.

### "Next dates after the one being viewed" no longer runs out, or comes up empty

Two faults in this list mode of the Event Occurrences element and the `{lre_occurrences}` tag:

- The list gradually ran out as the viewed date moved further into the future, even when the event continued for months.
- For an event with no stored dates, for example one added by an import or a form, the list was empty whenever a date was in the page address.

### Smaller fixes

- **Both forms of the date in the page address are recognised.** The new list modes read only `?occurrence=` and ignored `?lre_date=`, which is what calendar links use. Both now work, and `lre_date` wins when both are present.
- **The month grid no longer adds an empty-looking sixth row** to months that fit in four or five weeks.
- **Bricks query loops mixing repeating and one-off events are always in date order.** On some sites each repeating event's dates were grouped together.

## Added in build 1.7.7.3

These arrived in a build sent to a few sites in May and are new for everyone else.

### A default empty message for the occurrences tag

**Recurring Events → Settings → Dynamic Tags → Default Empty Message** sets the text the `{lre_occurrences}` tag shows when an event has no dates to list. Leave it blank to keep the original behaviour, which is no output.

### An empty message for one tag

Add `||` and your text to the end of a tag to set its empty message. This overrides the default.

```
{lre_occurrences:5:next_after_current||No further dates this term}
```
